## 二、NestJS 核心结构

### Controller、Service 与 Module

- `Controller` 负责接收 HTTP 请求、读取参数并返回响应。
- `Service` 负责具体业务逻辑和数据访问，不把业务规则堆在 Controller 中。
- `Provider` 是可以交给 Nest 容器创建和注入的对象，Service 是最常见的 Provider。
- `Module` 用于组织 Controller、Provider、导入项和导出项，明确功能边界。

NestJS 通过 IoC 容器管理对象创建和依赖关系。类只声明需要什么依赖，不负责手动创建依赖，这有利于模块替换和单元测试。

## 三、HTTP 请求生命周期

今天通过实际代码梳理了请求进入 NestJS 后的主要执行链：

```text
请求
  -> Middleware
  -> Guard
  -> Interceptor（执行前）
  -> Pipe
  -> Controller
  -> Service
  -> Interceptor（执行后）
  -> 响应

发生异常 -> Filter
```

各组件职责如下：

| 组件 | 核心职责 | 今日示例 |
| --- | --- | --- |
| Middleware | 所有请求进入时的公共处理 | 生成 `X-Request-Id`，记录方法、URL、状态码和耗时 |
| Guard | 判断请求是否允许进入 | 检查 `x-demo-token`，失败返回 401 |
| Pipe | 参数校验和类型转换 | 把路由参数转换为正整数，非法值返回 400 |
| Interceptor | 包裹 Controller 前后逻辑 | 设置响应头、统计耗时并统一包装响应 |
| Filter | 捕获异常并统一错误格式 | 将 `HttpException` 转换为包含状态码、路径和时间的 JSON |
| Service | 实现业务规则 | 查询、创建、更新和删除数据 |

这套划分的关键不是记住 API，而是知道约束应该放在哪里：权限交给 Guard，参数交给 Pipe，公共前后处理交给 Interceptor，异常交给 Filter，业务规则留在 Service。

4. `4.nest-pg`：将 PostgreSQL 能力抽成独立的全局动态模块，支持同步配置和异步配置。

自定义模块把数据库连接从业务代码中分离出来，业务 Service 只依赖数据库服务接口，不直接负责连接池的创建与销毁。这是从“接口能运行”走向“后端工程可维护”的关键一步。

## 五、PostgreSQL 工程实践

`4.nest-pg` 不只是建立数据库连接，还补充了服务运行所需的边界：

- 使用 `DATABASE_URL` 集中传入连接信息，避免把账号密码写死在源码中。
- 配置连接池最小和最大连接数，并校验 `min <= max`。
- 设置连接、空闲、查询和数据库语句超时。
- 支持 SSL 和 CA 证书配置。
- 所有查询通过参数数组传值，避免拼接用户输入造成 SQL 注入。
- 记录查询失败和慢查询。
- 提供事务回调，成功时 `COMMIT`，异常时 `ROLLBACK`，最后释放连接。
- 应用启动时执行数据库探测，失败时阻止服务带病启动。
- 应用关闭时结束连接池，实现优雅退出。

健康检查区分了两种状态：

- `/health/live`：只检查 Node.js 进程是否能够响应。
- `/health/ready`：检查 PostgreSQL 是否可用，并返回连接池状态；数据库不可用时返回 503。

这种区分可以让容器编排或网关判断“进程还活着”和“服务已经可以接收业务流量”是否同时成立。
