# PRD Requirements Builder

## 适用范围

当用户要求完成产品需求分析、撰写 PRD、把调研转成需求、补充验收标准、检查遗漏场景或明确 MVP 边界时使用本 Skill。它面向文档类、SaaS、AI 功能和协作产品，也适用于其他有明确功能需求的产品。

用户只要求视觉稿、代码实现、市场调研或用户访谈执行时，不自动生成完整 PRD，除非用户同时要求产品需求文档。

## 输入处理

优先读取用户提供的调研文档、竞品资料、已有 PRD、原型和约束。把材料分成四类并保留来源。

- 已知事实
- 用户或团队判断
- 基于材料的推断
- 尚未验证的假设

材料不足时可以做显式假设，但不能把假设写成已经发生的用户事实。缺失信息会影响范围或验收时，放入“待确认决策”，继续完成当前可交付部分。

## 固定工作流

1. 提取目标用户、核心问题、业务目标、成功指标和约束。
2. 定义产品定位、核心闭环、非目标和本期范围。
3. 生成标准 PRD 结构。具体章节和字段读取 [references/prd-schema.md](references/prd-schema.md)。
4. 将每个功能拆成带唯一 ID 的需求项。每条需求都必须包含场景、前置条件、主流程、异常流程和可自动化验收标准。
5. 建立异常流程矩阵。至少检查加载失败、空状态、输入校验、权限、网络断开、重复提交、并发冲突、超时重试、删除恢复、数据导入导出、通知失败和 AI 错误或无引用等场景。与当前产品无关的项必须明确标记“不适用”并说明原因。
6. 单独生成“不在本期范围”清单。每项至少说明排除原因、后续触发条件和替代处理方式，避免把未完成事项伪装成需求。
7. 运行 `scripts/check_prd.py <PRD 文件>`。检查失败时先修正文档，再交付结果。
8. 最终输出 PRD 文件、校验结果、关键假设和需要负责人拍板的事项。

## 需求项硬性格式

每个需求使用类似 `DOC-001`、`AI-002` 的稳定 ID，并包含以下字段。

- 需求标题与优先级
- 用户角色、使用场景和价值
- 前置条件与权限条件
- 主流程
- 异常流程
- 可自动化验收标准
- 数据、埋点、依赖和开放问题

验收标准必须能转成测试步骤，优先使用 `Given / When / Then` 或“给定 / 当 / 则”表达，至少覆盖一个成功路径和一个关键失败或边界路径。避免使用“体验良好”“性能较好”“支持正常”等不可判定描述，改成可观察的状态、字段、时间、权限或结果。

## 异常流程检查规则

异常流程不是统一套模板。先判断场景是否适用，再写处理方式和验收条件。对于适用场景，至少说明触发条件、用户看到的反馈、数据是否保留、是否允许重试以及是否记录日志。对不适用场景写出理由，例如“本期没有文件导入，因此导入格式降级不适用”。

AI 功能额外检查上下文范围、权限过滤、引用缺失、模型超时、结果为空、结果错误、用户确认和敏感内容处理。涉及创建任务、发送通知、修改权限、删除或恢复数据的动作，必须经过用户确认。

## 交付质量门槛

交付前确认以下条件全部满足。

- 目标用户和核心问题清楚，事实与假设有区分。
- 每条需求有唯一 ID、优先级和可自动化验收标准。
- 每条 P0 需求至少有一个成功验收和一个关键异常或边界验收。
- 异常流程矩阵已覆盖适用场景，未适用项有理由。
- “不在本期范围”清单独立存在，不与普通待办混写。
- 页面状态至少包含加载中、空状态、错误、无权限和成功状态。
- 权限、数据结构、埋点、非功能要求和发布门槛已写明或标记待确认。
- `check_prd.py` 返回通过。
