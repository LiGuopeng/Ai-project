# API、数据契约与安全规范

## 1. API 基线

API 应使用统一路由前缀、资源化路径和明确的 HTTP 语义：`GET` 查询、`POST` 创建、`PATCH` 更新、`DELETE` 删除。文档入口、版本策略和认证要求必须在项目 README 或 API 文档中明确记录。

资源路径使用复数名词；动作仅在无法用资源和 HTTP 方法表达时使用。分页、排序、过滤、幂等性和错误码在接口设计阶段明确，不靠调用方猜测。

## 2. 输入与响应

服务端必须在边界层校验输入，使用 DTO、Schema 或等价模型限制类型、长度、格式和可选字段。非法输入返回稳定、可理解的 4xx 响应，不把堆栈、SQL、内部路径或配置泄漏给调用方。

前端 API 类型集中在 `types/` 或共享包，服务函数返回明确的业务数据。错误消息通过统一工具转换，页面只展示用户可理解的信息。接口改动必须同步更新输入模型、输出类型、服务封装和文档。

正式业务数据不得由前端本地存储、内存数组或静态 mock 提供。即使是单机本地开发，也必须通过 API 写入项目配置的本地数据库；前端本地存储仅可保存不影响数据一致性的 UI 偏好。

## 3. 鉴权与数据隔离

需要访问控制的接口统一采用项目约定的认证机制；前端客户端集中注入凭证并统一处理未认证响应。每次资源读取、更新和删除都必须执行权限校验，不能仅凭资源 ID 操作数据。权限规则应靠服务端保证，不能只依赖前端隐藏按钮。

## 4. 配置和安全

密钥、密码、token 和生产跨域配置不能写入源码或提交仓库。`.env.example` 只放变量名和安全的开发默认值；生产通过环境变量或密钥服务注入。敏感信息不得出现在日志、错误响应、截图或测试 fixture 中。

数据库生产环境关闭自动同步表结构，使用迁移、备份和回滚策略。外部输入、文件上传、URL、重定向和日志内容都应按对应风险进行校验和脱敏。

## 5. 多实现一致性

多个服务实现同一 API 时，必须保持路径、状态码、字段命名、认证语义和持久化契约一致。任何一端修改协议，都要同步更新其他实现、共享类型、调用方和文档，并执行契约验证。
