# 测试与验证规范

## 1. 当前基线

参考工程已配置构建、类型检查、Lint、拼写检查和提交门禁，但没有独立的自动化测试脚本。因此不能把“构建通过”称为功能测试通过；交付时应分别报告静态检查、构建检查、自动化测试和手动验证结果。

## 2. 变更与验证映射

| 变更范围 | 最低验证 |
| --- | --- |
| Markdown、配置、规范 | 结构检查；涉及脚本时运行对应命令 |
| 类型或公共包 | 全量 typecheck、受影响包 build |
| 前端页面、路由或 service | 前端 build，手动验证加载、错误和空数据状态 |
| Next.js API、输入模型或持久化 | 服务端 typecheck/build，启动 Next.js 并验证成功和主要 4xx 路径 |
| 多服务契约 | 各实现启动、接口对照和共享类型检查 |
| Docker、环境变量或部署 | 配置检查、容器启动/停止、健康接口或连接验证 |
| 持久化业务功能 | API CRUD、数据库查询、刷新页面后的数据恢复验证 |

## 3. 测试命名与范围

前端组件或工具使用 `*.test.ts` / `*.test.tsx`，服务端按模块使用 `*.spec.ts`，Python 使用 `test_*.py`。测试目录应反映源码领域。至少覆盖主要成功路径、输入校验失败、未认证、资源不存在、权限隔离和外部依赖失败。

## 4. 手动验收清单

- 核心流程可以完成，并且成功结果可见。
- 加载、错误、空数据、重复提交和网络失败有明确反馈。
- 路由保护、权限边界和凭证失效行为符合预期。
- API 文档、代理、环境变量和数据库连接配置有效。
- 持久化数据不是来自浏览器本地存储或前端内存，而是通过 API 写入数据库。
- 没有产生未跟踪的构建产物、缓存、`.env` 或本地数据文件。

## 5. 失败处理

失败时保留错误输出并定位根因，不通过关闭规则、跳过检查或删除缓存掩盖问题。受环境限制无法运行的验证，必须在交付说明中写明命令、阻塞原因和后续建议。
